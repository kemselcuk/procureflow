## D001 — A modular monolith and one notification worker

Confirmed approach: Java 21/Spring backend with a complete Angular UI. Use a modular monolith for synchronous business operations and a separate worker for asynchronous notifications. Explicit package/module boundaries keep the important purchase, budget and audit transaction in one PostgreSQL database transaction. A small event-contract module can be shared; the worker does not import request/budget repositories.

Alternative: splitting purchasing, approvals and budgets into services would add distributed consistency work without helping this portfolio's initial goal. No Redis is needed for correctness: database constraints/locks and durable broker/database state cover the concrete requirements. Revisit additional infrastructure only for a measured requirement.

## D003 — Explicit company scope and scoped membership

Use a shared application schema with a non-null company key on tenant-owned records. Resolve the user by validated JWT issuer + subject, then an active membership; never take company authority from a request body, header, selected URL or opaque ID alone. The first release has one active company membership per identity.

Use Keycloak for authentication and Spring Security as a standard JWT resource server. The application membership/role assignments are the source of company-specific authorization; avoid two independently editable copies of the same business-role policy. Membership changes require company-administrator authority, and coarse authenticated routes never replace resource/action checks.

Re-read active membership and current application roles for commands rather than trusting business roles embedded in a still-valid token. Derive the submission department from the validated membership; client-provided company/department values cannot expand its scope. The plan owns the proposed role/state matrix, including visibility limits and changes after submission. This keeps revocation and department assignment in the same application policy instead of depending on token refresh timing.

Scope repository reads and mutations by company. Enforce composite company/entity foreign keys and unique constraints where relationships cross tables, including department/request/membership/notification relationships. An unscoped repository lookup must not become an authorization shortcut. Company administrators are not global administrators.

Row-level security and a database per company are alternatives. The initial design uses explicit scoping plus relational constraints and a comprehensive negative-test matrix to keep the policy visible in Java. It does not claim that one shared application database role prevents a malicious administrator or arbitrary SQL from reading all companies.

References: [Spring Security JWT resource server](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html), [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html). Validate issuer, signature, expiry and intended API audience; use a public SPA client with Code + PKCE, in-memory tokens and restricted redirects/origins. Local development OIDC configuration must not be presented as production configuration.

### P1 implementation contract

Separate authentication bootstrap from company authorization. A valid JWT may idempotently register only its own `(issuer, subject)` through `POST /api/identities/self`; this exposes no tenant data and never creates a company/membership/role. Company administrators may link that existing identity by opaque ID, without querying a global identity directory. All company endpoints re-read the current active database membership and explicit roles. Foreign resource IDs remain 404 and do not establish authority. The plan owns the endpoint matrix.

For commands, acquire a company-row shared lock before re-reading authorization; membership/role changes instead take an exclusive lock on that same company row. This serializes revocation against already-authorized commands without locking an arbitrary pair of administrators in conflicting order. Within a company, membership mutations are rare enough for this explicit coarse authorization lock. Subsequent purchase commands still acquire request then budget locks in D004 order, after the authorization guard; no command may invert these orders. Read endpoints recheck membership each call but do not hold a lock for an entire browser session. No cached token business roles are used.

Identity/membership scoping uses explicit SQL queries so composite tenant predicates and authorization locks are visible; monthly budgets use JPA mappings/repositories with explicit company predicates. Both participate in the same Spring database transaction. The database enforces one active company membership per identity, tenant-composite department/membership/budget relationships, explicit role values and unique scoped assignments. Application-level policy also prevents removing the last active company administrator. Database migration and application credentials are separated before business data is introduced; the application cannot alter schema or rewrite audit rows.

Keycloak 26.8.1 and keycloak-js 26.2.4 remain the selected stable versions after main-agent validation of the [official server release](https://github.com/keycloak/keycloak/releases/tag/26.8.1), [npm metadata](https://registry.npmjs.org/keycloak-js/26.2.4) and [Quay tag/manifest metadata](https://quay.io/api/v1/repository/keycloak/keycloak/tag/?filter_tag_name=eq:26.8.1). Server release notes enumerate security fixes; repository advisories alone are not an exhaustive advisory feed. The image has a multi-architecture immutable digest, not a claimed publisher-signature verification.

The local realm has a public client with Code flow only, required S256, exact frontend root redirects/origins, no direct/password grants, and an access-token-only custom API audience. Passwords are environment placeholders, never committed values. An external loopback issuer and separate container-reachable JWKS URL allow signature validation without trusting forwarded/client headers. Tokens stay in adapter memory, and the interceptor attaches them only to same-origin private `/api/` requests after refresh. Database membership is authoritative even when token claims advertise administrator roles. The local HTTP realm (`start-dev`, loopback-bound ports) is explicitly not production OIDC configuration.

The repeatable provider probe uses actual authorization forms, cookies, code exchange, PKCE, refresh and logout over HTTP plus real protected API calls; it is not password grant and not a mock provider. This proves server/protocol integration, not rendering or the adapter's behavior in a real browser. Angular adapter behavior has separate service/interceptor tests; rendered browser journeys remain for the frontend/system phases. Scoped application data and access boundaries must still pass independent security review before P1 acceptance.

## D004 — Final approval owns the budget transaction

The plan's fictional budget is accounting data, separate from the user's real infrastructure reserve. Pending requests do not reserve funds. Final approval uses a single command timestamp to identify the UTC approval month and locks the request row before its company/department/month budget row. Recheck state, current membership/role, requester separation and previous approver before charging.

Use database row locks under a documented isolation level (initially PostgreSQL READ COMMITTED) rather than a JVM mutex. Different app instances must obey the same invariant. Requests use decimal amounts and fixed scale; budget checks live in the transaction and database constraints. A unique request charge plus unique approval-step records backstop duplicate execution. State, charge, usage, audit and outbox are atomic.

All commands needing both rows use the same lock order. Budget limit changes lock the budget and cannot lower the limit below usage. Explicit conflicts are preferable to a successful response with inconsistent effects. Freeze amount/department after submission; terminal approved requests have no cancellation/refund path in this release.

Optimistic locking and conditional SQL updates are alternatives. Pessimistic locking makes the shared budget contention and correctness argument explicit for this scope. A version field can detect stale UI commands, but it does not replace the shared-budget lock. Tests must use separate transactions/connections and barriers, including rollback and approval/cancel races.

Reference: [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html) documents conflicting row locks and consistent acquisition order. Use short database transactions without broker/SMTP calls while holding purchase/budget locks. Configure bounded lock/transaction waits and return a retryable conflict where appropriate; no silent retry may duplicate business effects.

### P3 implementation contract

Approval uses an expected version and explicit 409 on completed/stale retries, rather than extending the create/submit result cache. Lock current company authorization, then the scoped request; capture one UTC instant after the request lock and before the budget lookup, and charge its UTC month. A shared budget application service joins the caller's existing transaction, locks the JPA budget entity, checks remaining funds, flushes usage/version and inserts a unique tenant-linked charge. Request commands do not import the budget repository. This preserves the existing administrator budget-lock path and makes JDBC request/history/outbox writes participate in the same transaction as JPA usage updates.

Append-only approval steps bind actor/membership, request version/history, timestamp and correlation; unique step and request/actor keys prohibit duplicate or same-actor two-step approval. A unique charge binds company, request, department, budget period and final approval version. Deferred settlement checks validate the completed approved request/step/charge relationship at commit without taking a request FK lock before the explicit request lock. These checks complement, not replace, application authorization and the atomic usage update. Nullable `approvedAt` and derived UTC `budgetMonth` expose the actual charging period; submitted time never chooses that month. No budget reservation or automatic missing-month creation is introduced.

## D005 — Transactional outbox with at-least-once delivery

Business transactions insert an event into PostgreSQL; they never require a successful RabbitMQ connection to commit a purchase operation. The relay claims pending rows with a recoverable lease, publishes outside the purchase transaction, uses persistent messages/durable topology and checks mandatory routing plus publisher confirms. Only then does it mark a row published.

A relay crash after confirmation but before its database update can publish the same event again. Preserve stable event IDs. The worker uses an inbox/unique delivery key and commits in-app notifications and email-job records atomically before acknowledging the broker message. It validates recipient/company relationships and mutates no purchase/budget tables. Use separate database credentials/grants where practical to enforce that boundary.

Retry transient failures with bounded backoff; malformed/unsupported poison events go to visible quarantine/dead-letter handling. A documented authorized replay uses the same event ID and safe deduplication. Multiple relays/workers must claim safely if later scaled; local deployment uses one of each and one broker, with no high-availability claim.

[RabbitMQ publisher confirms and consumer acknowledgements](https://www.rabbitmq.com/docs/confirms) describe different stages of delivery. A publisher confirmation is not a business-consumer acknowledgement. Durable broker/database volumes and explicit restart tests are required; topology flags alone are not recovery evidence.

### P4 implementation proposal (under challenge)

Keep all asynchronous runners in the separate worker process so a missing broker cannot prevent the business app from starting or approving purchases. Immutable outbox events are the authoritative source; mutable dispatch leases live in a separate tenant-linked table, initialized/backfilled by the migration/capture path. Use database-clock leases, unique fencing tokens and conditional completion updates; never hold a database transaction while publishing or sending SMTP. A consumer commits inbox/delivery/in-app/email-job effects before acknowledging. It compares received data with the canonical snapshot and revalidates membership under the same company authorization barrier as administration. Expose a narrowly scoped database locking function if PostgreSQL's row-lock privileges would otherwise require granting the worker company-update authority; the function needs a fixed search path and restricted execution grants. Shared event records remain independent of application repositories.

Alternatives are an app-hosted relay or direct post-commit broker publication. The former couples broker lifecycle/dependencies to the request process; the latter loses recovery after a committed purchase/process crash unless backed by the same durable outbox. A single worker process may run several separately fenced runners without introducing another service. Dispatch and SMTP failures use bounded backoff/quarantine and explicit operator replay, not unbounded immediate requeue. The plan owns exact routes, claim/replay semantics and the failure acceptance cases. This proposal requires independent review and real-service proof before acceptance.

### Relay implementation choices

The reviewed relay claims one event immediately before its own publication, with a bounded per-poll work limit. Preclaiming a batch for sequential network sends could expire later leases without attempting their work; merely increasing lease duration hides rather than removes that scheduling dependency. Completion/failure first locks the exact dispatch row in a short database-only transaction, then checks its token and live database clock. Transaction-start `now()` is insufficient after a lock wait crosses expiry. Claim and exhausted-work selection use materialized, bounded `SKIP LOCKED` CTEs: a rescanned locking `IN (SELECT ... LIMIT ...)` can make the effective row bound depend on the query plan, and an unbounded cleanup UPDATE can block otherwise independent claims.

The local topology is a durable topic exchange and classic durable queue, with persistent messages and mandatory routing plus correlated publisher confirms. A classic queue on one broker is deliberate; no quorum replication or high availability is implied. A return defeats an ACK. The same-container restart test covers local persistence, not host loss or failover. The RabbitMQ upstream entrypoint needs ownership/privilege initialization, so that container does not inherit the application's read-only-root and dropped-capability settings; it retains loopback host bindings, a dedicated data volume and no-new-privileges. The plan records actual test evidence, integration status and remaining app-outage/consumer/SMTP gates.

### Consumer retry contract (implemented and locally verified)

For the bounded local consumer, retaining one manually unacknowledged delivery through a small bounded number of attempts with interruptible backoff is an acceptable first implementation. Every attempt uses a short independent database transaction; no database connection/transaction is retained during backoff. A stable sanitized diagnostic fingerprint and attempt evidence survive process redelivery. A permanent invalid message or exhausted attempt budget must have durable, distinguishable quarantine evidence before ACK; if that persistence fails, the original delivery must remain recoverable. Materialization success likewise commits before ACK. The consumer must not confuse a relay publisher confirmation with its own database commit.

This favors a simple local correctness argument over retry throughput: a waiting delivery occupies a bounded listener slot. Immediate requeue would hot-loop poison messages; ordinary classic-queue dead-letter forwarding introduces an avoidable unconfirmed republishing window. No extra retry service or broker topology is added without a concrete need. Terminal evidence and explicit privileged canonical-event replay are demonstrated under the existing schema/grants; recovery during diagnostic-access failure retains the delivery with capped interruptible backoff rather than acknowledging without durable evidence. Unknown malformed payloads retain a hash/code, not arbitrary body content, so the hash alone cannot reconstruct them for replay. Actual checks and remaining hosted gates are in the plan.

Operator replay distinguishes unknown malformed input from a **valid canonical message whose canonical lookup temporarily failed**. Both can have NULL-scoped hash diagnostics, but only the latter can be matched safely to a selected immutable canonical event. The shared maintenance SQL derives that event's exact publisher-byte transient fingerprint and clears only that exact NULL-scoped `materialization_failed` record, together with the selected event's scoped diagnostics. It does not broadly clear unscoped records, reset another event/company or reopen normal redeliveries automatically. PostgreSQL's built-in SHA-256 avoids a new extension/grant; equality with the Java fingerprint, scope/lease refusals and real broker recovery passed independently. The unknown malformed payload remains unreconstructable from its hash alone.

## D006 — Durable SMTP jobs and an explicit limitation

The integrated smoke fixture distinguishes recovery **after the worker/dependency reports ready** from total elapsed time since a deliberate stop. Startup and the intentionally held outage are not assumed instantaneous. Both time origins are reported; the 60-second readiness-relative bound is not an outage-duration or availability promise. In the independently observed candidate, the entire stopped-worker fixture also finished within 60 seconds, but the SMTP stop-to-completion interval did not. Wait helpers reject observations after the original monotonic deadline; fake-clock regressions cover the boundary and supplied origins. The plan records actual values and limitations; no SLA or hidden acceptance waiver is implied.

The mail implementation uses the Boot-managed starter without independent dependency overrides. The resolved worker tree contains Boot mail modules 4.1.1, Jakarta Mail API 2.1.5, Jakarta Activation API 2.1.4, Angus Mail 2.0.5 and Angus Activation 2.0.3. A point-in-time public OSV query of those six resolved coordinates/versions returned no reported vulnerabilities; retained local evidence is `target/p4-mail-dependency-osv.json` and the worker's generated dependency tree. This is package-database evidence, not an exhaustive security or container-image assessment.

The notification worker separately leases database email jobs, sends to local Mailpit and records success/failure. Message IDs and correlation IDs allow observations to be matched to jobs. In-app creation and email-job materialization are idempotent per event/recipient/channel.

SMTP acceptance and saving “sent” to PostgreSQL are not one atomic transaction. A crash in between may cause a duplicate email on retry. A stable Message-ID is useful for correlation but does not guarantee that SMTP recipients deduplicate. Promise eventual completion after a temporary worker outage and unique database effects, not exactly-once external email delivery. Test the ordinary redelivery path and document the ambiguous acceptance window.

Mailpit is local demonstration infrastructure, not a real transactional email provider. Permanent delivery failures are visible and require correction/replay; “eventually completes” assumes recoverable infrastructure and valid recipients.

P4 initially addresses only fictional local Mailpit recipients as `<identity UUID>@demo.invalid`, derived from the validated snapshot rather than a user-supplied address or JWT claim. No real email address directory or external provider is introduced. Revalidate membership at each SMTP claim, then send outside the transaction; a concurrent revocation cannot recall an already-authorized/in-flight SMTP operation. Persist SKIPPED ineligible jobs and preserve that outcome across ordinary replay. Real-recipient routing would require a separately designed verified-address/privacy contract and is not implied by local notification delivery.

## D007 — Database migrations, fixtures and audit evidence

Flyway is the schema owner; JPA validates it. Never use Hibernate `update` as a substitute for migrations. Versioned migrations add tenant constraints, indexes, unique charges/steps and outbox/notification tables. Keep local/demo data explicitly enabled and separate from production schema migrations and CI-specific fixtures.

Audit rows are append-only through application behavior and restricted application permissions where practical. Capture business transitions in the same transaction; external application logs are not an authoritative substitute. Do not claim cryptographic tamper-proof history or regulatory certification. Avoid logging credentials/tokens and minimize event payloads.

## D011 — Request commands, retries and event capture

Request persistence uses explicit company-scoped SQL, matching the visible tenant predicates and authorization barrier already used by directory commands. Lock order is company authorization barrier, create/submit command-key claim, then request row; P3 adds the budget lock after the request. No broker or network call occurs inside the business transaction. PostgreSQL READ COMMITTED plus unique command keys and request row locks handles multiple application instances; a JVM mutex would not.

Create/submit insert a transaction-local command-result claim using `INSERT ... ON CONFLICT DO NOTHING`. A competing insertion waits for commit/rollback; after a committed conflict a new statement reads and validates the canonical command fingerprint and original response. The winner writes that response before commit. A rolled-back business/history/audit/outbox write also rolls back the claim. Replays still require current company membership and command authority; a cached response must never bypass revocation. Edit/cancel/reject instead have explicit expected-version conflict semantics, not an undocumented silent retry.

The claim intentionally has **no request FK**: inserting such a FK before the explicit request lock could take an implicit KEY SHARE lock and create a lock-upgrade deadlock between distinct submit keys. The target is bound inside the fingerprint; scoped existence/ownership is checked before claiming, then the request is locked for mutation. A deferred database constraint rejects unfinished command claims at commit. Fingerprints omit mutable membership/department data. Waiting is bounded by the configured lock timeout, reported as a retryable conflict; callers retain the same key.

Requests capture department at creation; an edit explicitly refreshes a draft's department from current membership. Submit rejects a stale department rather than silently routing the request elsewhere. PostgreSQL also rejects invalid state edges, nonpositive amounts, version jumps and changes to submitted content. History and outbox records remain append-only through runtime grants. Correlation IDs tie a command's request/history/audit/event records together; they are server-generated and are not authentication credentials.

Capture each command's UTC instant once at PostgreSQL microsecond precision, truncating finer clock precision before persistence and event serialization. This avoids an envelope/database timestamp mismatch and prevents database rounding from moving a near-month-boundary timestamp into a different budget month in P3. Versions, not timestamps alone, order request history.

The shared event module contains only immutable versioned records, not repositories or application services. Recipient snapshots use tenant-linked membership/identity keys, include both future channels, and omit free-text content. This preserves a stable producer/consumer contract without giving the worker access to purchase repositories. Delivery-time membership validation and at-least-once processing remain P4 acceptance requirements. The plan owns exact API scopes, transition recipients and retry responses.

### P7 clarification — restart is not broker recreation

Independent handoff review identified that the local broker has a named volume but no fixed hostname or `RABBITMQ_NODENAME`. The [official RabbitMQ image documentation](https://github.com/docker-library/docs/blob/master/rabbitmq/README.md#running-the-daemon) explains that its node name/data location defaults to the hostname; a newly created container can therefore use a different node directory in the same volume. `DispatchStore` claims pending/expired-leased work, not already published events, so an empty replacement queue is not automatically repaired by the outbox relay. Existing broker persistence/recovery tests retain the same container across stop/start and make no recreation claim.

Choose the minimal safe handoff correction: recommend stop/start for routine pauses and explicitly prohibit treating down/up volume retention as a message-preservation guarantee. Do not silently assign a new fixed hostname to an existing populated volume: that also changes node identity and needs a deliberate data/migration decision. A stable-node configuration plus a queued published-event recreation regression is a possible future improvement, not implemented or accepted here. PostgreSQL state surviving recreation is separate evidence, and neither restart path is a backup/restore test.

## D016 — One-shot schema ownership and scheduler isolation

Move Flyway into a one-shot `migrate` service instead of running it inside the long-lived application process. Only that container (and the PostgreSQL initialization step on an empty volume) receives `MIGRATION_DB_PASSWORD`; the app starts with `SPRING_FLYWAY_ENABLED=false`, depends on `service_completed_successfully` and validates the schema through JPA. This keeps the runtime credential unable to alter schema or rewrite append-only business tables, at the cost of a startup dependency and a new one-shot container in the local topology. An external migration job is the production alternative; a `start --wait` invocation must name the seven long-running services because an exited one-shot container is not a valid wait target.

The current app-side fail-closed behavior is structural JPA validation plus the Compose dependency. That is sufficient for V1–V5 because they add tables/columns, but an index-only future migration could pass structural validation while the schema is stale. Before P8.2 introduces V6, add an app-side check of the latest `flyway_schema_history` version (or an equivalent marker) and a negative startup test; do not treat this decision as that guarantee.

Run the outbox relay and SMTP runner on separate scheduler capacity (`spring.task.scheduling.pool.size: 2`) so a blocked SMTP peer cannot starve publication. `fixedDelay`, fenced database leases, consumer ACK semantics and the worker's bounded pool/timeouts stay unchanged. This is local process isolation, not HA or a throughput guarantee.

## D017 — Browser security defaults and bounded request bodies

Serve the SPA with a header CSP that keeps `script-src 'self'` and adds `frame-ancestors 'none'`, `X-Frame-Options: DENY`, COOP and the existing nosniff/referrer headers. Disable Angular critical-CSS inlining so the built `index.html` has no inline script/style; `style-src 'unsafe-inline'` remains only for Angular's runtime component styles. The local CSP permits loopback Keycloak origins on any port because the development issuer port is configurable; a non-loopback deployment must pin the exact issuer origin and add TLS/HSTS there. Do not weaken script policy to make a local shortcut work.

Bound request bodies at both layers: nginx 64 KiB and an application JSON filter of 16 KiB that rejects declared and chunked oversize with `413 payload_too_large` before deserialization, while authentication still runs first. The filter is not a general multipart/streaming limit; no such endpoint exists in this product.

The frontend pins a narrow `@angular/build → vite 8.3.4` npm override to clear a dev-tooling advisory (the nested 8.3.0 was vulnerable). The override is tested with the exact lock, 469 tests, production build and audit; `npm audit fix --force` and the resulting Angular downgrade are rejected. Vite is build/dev tooling and is not part of the shipped browser bundle. This is not a blanket dependency-upgrade policy.
